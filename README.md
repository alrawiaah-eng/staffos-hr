# StaffOS — إدارة الموظفين والإجازات

هذه النسخة تجمع نواة نظام الموظفين والإجازات مع نموذج HR الأوسع داخل تطبيق واحد. النسخ الأصلية بقيت محفوظة خارج هذه النسخة.

## الوحدات المدمجة

- الموظفون، الأقسام، الصلاحيات، المستمسكات، السجلات، الإجازات، الموافقات والتنبيهات وسجل التدقيق.

تطبيق ويب فعلي لإدارة الموظفين والإجازات، بواجهة عربية RTL متجاوبة، دون اسم شركة أو شعار. React + Vite للواجهة، Express لواجهة API، وPostgreSQL لحفظ جميع البيانات والمرفقات والجلسات.

## التشغيل المحلي السريع

على Windows، بعد تثبيت المتطلبات وبناء المشروع، انقر مرتين على **Start-HR.cmd**. يعيد تشغيل الخادم في الخلفية عند الحاجة، ويفتح التطبيق في المتصفح. يمكن استعمال الملف أيضًا بعد إعادة تشغيل الكمبيوتر. سجلات التشغيل في `data/server-output.log` و`data/server-error.log`.

عولجت مشكلة إعادة فتح قاعدة البيانات داخل مجلدات Windows/OneDrive الموسومة للقراءة فقط: يعيد التطبيق ضبط سمة مجلدات قاعدة البيانات عند البدء، دون حذف البيانات أو إعادة تهيئتها.

المتطلبات: **Node.js 22.12 أو أحدث**. يوصى بـ Node.js 24. يمكن استخدام npm أو pnpm؛ ملف قفل pnpm مرفق للإصدارات القابلة لإعادة البناء.

من مجلد المشروع:

```sh
npm install
npm run build
npm start
```

افتح **http://localhost:3000**. لا تحتاج إلى إنشاء `.env` لتجربة النسخة المحلية. عند التشغيل الأول تُنشأ البيانات التجريبية تلقائيًا. البيانات تحفظ في `data/postgres`، وتبقى بعد إغلاق التطبيق وإعادة تشغيله.

للتثبيت بنفس الإصدارات التي تم التحقق منها:

```sh
npm install -g pnpm@11.19.0
pnpm install --frozen-lockfile
pnpm build
pnpm start
```

الوضع الافتراضي يستخدم **PGlite**، وهو PostgreSQL مدمج يعمل داخل الخادم، وليس تخزينًا في المتصفح. مناسب لتجربة محلية بعملية خادم واحدة. التشغيل السحابي يستخدم PostgreSQL القياسي عبر `DATABASE_URL`.

### حسابات التجربة

كلمة المرور لكل الحسابات: **`DemoPass!2026`**.

| اسم المستخدم | الدور |
|---|---|
| `employee` | Employee — موظف |
| `manager` | Department Manager — مسؤول قسم |
| `hr` | HR Officer — موظف موارد بشرية |
| `hrmanager` | HR Manager — مدير موارد بشرية |
| `director` | Approver / Director — مدير أو مخوّل |
| `admin` | System Admin — مدير النظام |
| `auditor` | Auditor — مدقق |

البيانات افتراضية: 12 موظفًا، 4 أقسام، 7 حسابات، أرصدة، سجلات تدريب وشكر وتكريم، وطلب إجازة تجريبي. لا تتضمن صور مستمسكات حقيقية؛ ارفع صورًا تجريبية لاختبار المستمسكات والتنبيهات.

## مكان بيانات التشغيل

على Windows تُحفظ قاعدة البيانات افتراضيًا خارج مجلد المشروع، في `%APPDATA%\StaffOS\data\postgres-v2`، بعيدًا عن مزامنة OneDrive. أما السجلات ومفتاح تشفير المستمسكات فيبقيان في `data/` داخل المشروع.

**المفتاح هو أخطر ملف في النظام.** بفقدانه تصبح كل صور المستمسكات المخزّنة غير قابلة للفتح نهائيًا، ولا سبيل لاستعادتها. وهو مستبعد من Git عمدًا، فاحتفظ بنسخة منه في مكان آمن منفصل.

عند أول تشغيل على جهاز جديد، يُنشأ المفتاح بجوار قاعدة البيانات في `%APPDATA%\StaffOS\data` لكي يبقيا معًا. أما إذا وُجد مفتاح داخل `data/` في المشروع فيبقى مستعملًا كما هو ولا يُنقل، لأن تغيير مكانه يعني تعذّر فتح المستمسكات المشفّرة سابقًا.

لتجميع كل بيانات التشغيل في مكان واحد خارج المزامنة، اضبط `STAFFOS_DATA_DIR`. إذا كان لديك مفتاح قائم في `data/document.key` فانسخه إلى المكان الجديد **قبل** ضبط المتغير، وإلا أُنشئ مفتاح جديد وتعذّر فتح المستمسكات القديمة.

أنشئ ملف `.env` وأضف سطرًا واحدًا:

```
STAFFOS_DATA_DIR=C:\Users\<اسم المستخدم>\AppData\Local\StaffOS
```

لنقل بياناتك الحالية إلى المكان الجديد قبل أول تشغيل، أغلق التطبيق ثم انسخ المجلد:

```
robocopy "data" "%LOCALAPPDATA%\StaffOS" /E
```

النسخ لا يحذف الأصل، فيبقى `data/` كما هو حتى تتأكد من سلامة التشغيل. وإن تُرك `STAFFOS_DATA_DIR` فارغًا أو غير موجود، فلا يتغير شيء عن السلوك الحالي.

## البديل في العمل أثناء الإجازة

حقل **البديل** في طلب الإجازة يقابل خانة *Replacement if Applicable — البديل في العمل* في استمارة الإجازة الورقية، ويبقى اختياريًا كما في الورقة. متى اختير بديل تحقق النظام من أربعة شروط قبل قبول الطلب:

- أن يكون من **قسم مقدّم الطلب نفسه**، وأن يكون نشطًا على الملاك، وألّا يكون الموظف بديلًا لنفسه.
- ألّا يكون **مجازًا** في فترة متداخلة.
- ألّا يكون **مكلّفًا بتغطية زميل آخر** في فترة متداخلة.

ويمنع النظام العكس أيضًا: من كُلّف بالتغطية عن زميل لا يستطيع تقديم إجازة تتداخل مع فترة تغطيته، حتى لا تبقى إجازة سابقة بلا بديل فعلي دون أن ينتبه أحد.

قائمة البدلاء في النموذج تُبنى بعد إدخال التاريخين وتعرض زملاء القسم المتاحين فعلًا، وتذكر عددهم من أصل عدد زملاء القسم. وإذا لم يبق أحد متاحًا ظهر السبب صراحةً بدل قائمة فارغة. يصل البديل إشعار بتكليفه، ويظهر اسمه في جدول الإجازات وبطاقة الموافقة وتفاصيل الطلب.

## ما يتضمنه الإصدار

### استكمال الإصدار الأول

- **الصورة الشخصية للموظف:** من «الملف الوظيفي ← البيانات الشخصية ← إضافة صورة شخصية». JPG/PNG حتى 5 ميغابايت، مع معاينة قبل الإرسال. صورة الموظف لنفسه تحتاج موافقة HR من «الموافقات ← الصور الشخصية»، وتبقى الصورة المعتمدة السابقة إلى حين الاعتماد. يستطيع HR حفظ صورة موظف آخر مباشرةً. الصور مشفرة، ومتاحة لصاحب الملف وHR فقط، ولا تُعرض للعامة.
- بعد تحديث ملفات المشروع بينما التطبيق مفتوح، انقر مرتين على `Restart-HR.cmd` لتفعيل الخادم المحدّث، ثم حدّث صفحة المتصفح. يحافظ ذلك على البيانات الموجودة، ولا يعيد تهيئة قاعدة البيانات.

- جميع تواريخ الإدخال والعرض بصيغة **DD/MM/YYYY — يوم/شهر/سنة**، بما فيها الميلاد والعقود والمستمسكات والإجازات والدورات والتقارير. يمكن الكتابة بالأرقام العربية أو الإنجليزية، أو الاختيار من تقويم المتصفح/النظام. يحفظ الخادم التاريخ بصيغة ISO داخل قاعدة البيانات لضمان الفرز والحساب الصحيح.
- تعديل الدورات وكتب الشكر والتكريم بواسطة HR، مع استبدال المرفق أو إزالته عند الحاجة وتسجيل القيم السابقة والجديدة.
- تبويب «رصيد الإجازات» داخل ملف الموظف: الاستحقاق والمستخدم والمحجوز والمتاح لكل سنة. صلاحية `leave.balance` متاحة افتراضيًا لمدير HR؛ تعديل الاستحقاق يحتاج سببًا ولا يسمح بخفضه عن المستخدم والمحجوز.
- ملف `Start-HR.cmd` لتشغيل Windows بالنقر المزدوج، وإصلاح إعادة فتح قاعدة البيانات داخل مجلدات OneDrive.

- تسجيل الدخول والخروج، كلمات مرور مجزأة باستخدام scrypt، جلسات مخزنة في قاعدة البيانات بمدة 8 ساعات وملفات ارتباط HttpOnly / SameSite، وحماية CSRF وتحديد محاولات الدخول.
- لوحة تحكم لكل حساب بحسب نطاق الدور، وروابط للخدمة الذاتية والموافقات والأرصدة والتنبيهات.
- دليل الموظفين والبحث والتصفية حسب القسم، وإضافة الموظفين وتعديل بياناتهم الوظيفية بواسطة HR.
- ملف الموظف: الرقم والاسم والقسم والموقع والمسمى والمباشرة والعقد والحالة والراتب بصلاحية مستقلة؛ الهاتف والبريد والعنوان والميلاد والجنسية والحالة الاجتماعية والعائلة والطوارئ؛ المؤهلات والتاريخ الوظيفي.
- الموظف يقترح تعديل بياناته الشخصية فقط؛ تبقى القيمة السابقة معتمدة إلى أن يراجع HR المقارنة ويوافق أو يرفض مع السبب.
- صور الهوية وبطاقة السكن وعدم المحكومية تتطلب front/back. الجواز وإجازة السوق اختياريان. الصور المقبولة PNG/JPEG، حتى 5 MB لكل وجه، وتخضع للتدقيق. لا يجوز اعتماد المستمسك الشخصي من صاحبه.
- الدورات وكتب الشكر والجوائز مع التاريخ والجهة والملاحظات ومرفق اختياري PNG/JPEG/PDF، تديرها HR.
- طلب الإجازة، المراحل، سجل القرار، الرفض مع السبب، وإلغاء الموظف لطلبه قبل الاعتماد النهائي.
- إدارة الحسابات: إضافة، تغيير الدور، تعطيل الحساب، إعادة تعيين كلمة المرور. تغيير الحساب ينهي جلساته الحالية.
- إدارة صلاحيات كل دور ومتابعة أثر التغيير مباشرةً. لكل حساب دور واحد في V1، ويمكن تعديل قائمة صلاحيات الدور.
- إدارة الأقسام ومسؤول الموافقات لكل قسم.
- إشعارات داخل التطبيق للطلبات والقرارات، وتعليم الإشعارات كمقروءة.
- تنبيهات المستمسكات المنتهية أو التي تنتهي خلال 30 يومًا؛ فحص عند التشغيل، وكل ساعة أثناء عمل الخادم، وعند فتح الإشعارات. التنبيه لا يتكرر لنفس المستمسك وتاريخ الانتهاء والمستخدم.
- تقارير الموظفين والأرصدة، الإجازات، المستمسكات الناقصة والمنتهية، والتدريب والتكريم؛ تصفية حسب القسم والتاريخ حيث ينطبق، وتصدير CSV قابل للفتح في Excel، وطباعة أو حفظ PDF عبر المتصفح.
- Audit Log للعمليات وفتح الملفات، مع قبل/بعد عند التعديل؛ واجهة للقراءة فقط، ومشغّل PostgreSQL يمنع UPDATE/DELETE للسجل.

## قواعد الصلاحيات

تطبّق الصلاحيات في الخادم عند كل طلب، وليس بإخفاء أزرار الواجهة فقط.

| الدور | النطاق الافتراضي |
|---|---|
| Employee | سجله وطلباته ومستمسكاته وسجلات تطويره فقط |
| Department Manager | موظفو قسمه وسجل الإجازات والتقارير الخاصة بالقسم؛ يعتمد الطلبات التي هو مسؤولها المعين |
| HR Officer | إدارة الموظفين والمستمسكات والتطوير وتعديلات البيانات وموافقات HR؛ لا يرى الراتب |
| HR Manager | صلاحيات HR إضافة إلى عرض/تعديل الراتب وسجل التدقيق |
| Director | نظرة عامة وتقارير وموافقة المدير عند وصول الطلب لمرحلته |
| System Admin | الحسابات والصلاحيات والأقسام والتدقيق؛ لا يرى الرواتب أو صور المستمسكات افتراضيًا |
| Auditor | تقارير ومراجعة المستمسكات والتدقيق؛ دون صلاحيات تعديل تشغيلية |

تبقى الخدمة الذاتية متاحة لجميع الأدوار. البيانات الشخصية التفصيلية متاحة لصاحب السجل وHR؛ لا تظهر لمسؤول القسم افتراضيًا. محتوى قبل/بعد الحساس في Audit Log لا يظهر للأدوار التي لا تملك مراجعة بيانات HR. صلاحية الراتب منفصلة حتى عن إدارة النظام.

لا يمكن لأي مراجع اعتماد إجازته أو تعديل بياناته أو مستمسكه بنفسه. لا يمكن تعطيل أو تخفيض دور آخر مدير نظام نشط. أي توسعة لصلاحيات الدور تؤثر على جميع مستخدميه، لذا راجع اختيار الصلاحيات قبل حفظه.

## سياسة الإجازات التجريبية

هذه **سياسة تشغيل للـMVP**، وليست تطبيقًا لقانون عمل أو سياسة شركة بعينها:

1. سنوية، مرضية، وبدون راتب. الاستحقاق السنوي الافتراضي 30 يومًا لكل سنة؛ الخصم من السنوية فقط.
2. تُحسب أيام تقويمية، شاملة يوم البداية والنهاية، دون استبعاد نهاية الأسبوع أو العطل الرسمية.
3. المسار: **Employee → Department Manager → HR → Director عند الحاجة → Approved**.
4. موافقة المدير مطلوبة للإجازة بدون راتب أو المدة التي تتجاوز 7 أيام.
5. عند عدم وجود مسؤول قسم مؤهل أو إذا كان صاحب الطلب هو المسؤول نفسه، يبدأ الطلب من HR. أهلية المسؤول تعني حسابًا نشطًا وصلاحية `leave.manager`.
6. يمنع الطلب بتاريخ سابق، والنطاق غير الصحيح، والتداخل مع طلب غير مرفوض/ملغى. يجب فصل الطلب الذي يعبر نهاية السنة إلى طلبين.
7. تُحتسب الطلبات السنوية المعلقة ضمن الرصيد المحجوز عند تقديم طلب آخر، لكن الخصم الفعلي يحدث عند الموافقة النهائية فقط.
8. الانتقالات والخصم وسجل القرار والإشعارات ضمن معاملة PostgreSQL مع قفل للسجلات؛ لا يحدث خصم مكرر عند الموافقات المتزامنة.
9. الرفض ينهي المسار ويحتاج سببًا. الإلغاء الذاتي متاح فقط قبل الاعتماد النهائي، ولا توجد استعادة لإجازة معتمدة في V1.
10. عيّن مسؤول القسم من حساب admin في «المستخدمون والصلاحيات → الأقسام ومسؤولوها». إزالة المسؤول تحيل طلبات مرحلة القسم إلى HR. عند نقل مسؤول أو تعطيله، أعد تعيين مسؤول القسم أو أزل تعيينه لتوجيه الطلبات المعلقة.

## سيناريو تجربة كامل

1. ادخل بحساب `employee` وافتح الملف الشخصي، ثم «طلب تعديل بياناتي». أرسل تعديل الهاتف، وتحقق من بقاء الهاتف القديم في الملف.
2. ارفع صورة تجريبية أمامية وخلفية للهوية مع تاريخ انتهاء خلال 30 يومًا.
3. قدّم إجازة سنوية قصيرة بتواريخ لا تتداخل مع الطلب التجريبي الموجود.
4. سجل الخروج وادخل بحساب `manager`، وافق على الطلب من شاشة الموافقات.
5. ادخل بحساب `hr`، اعتمد تعديل البيانات والمستمسك والإجازة. يتغير الهاتف وتُخصم الإجازة بعد الاعتماد.
6. جرّب طلب «بدون راتب» لتظهر مرحلة `director` بعد HR.
7. ادخل بحساب `auditor` لمراجعة سجل العمليات، وبحساب `admin` لمراجعة الحسابات والأدوار والأقسام.

## تشغيل PostgreSQL القياسي محليًا

المتطلبات الإضافية: Docker Desktop، أو خادم PostgreSQL 17 متاح.

انسخ `.env.example` إلى `.env`، ثم أضف:

```dotenv
POSTGRES_PASSWORD=choose_a_strong_local_password
DATABASE_URL=postgresql://hr_app:choose_a_strong_local_password@localhost:5432/hr_leave
```

```sh
docker compose up -d db
npm run db:migrate
npm run db:seed
npm run build
npm start
```

رمّز الأحرف الخاصة في كلمة المرور داخل connection URL. تبديل `DATABASE_URL` يغيّر قاعدة البيانات المستعملة؛ **لا ينقل تلقائيًا** بيانات PGlite إلى PostgreSQL الجديد. استخدام `SEED_DEMO=true` في بيئة غير إنتاجية يضيف بيانات التجربة إذا كانت قاعدة المستخدمين فارغة.

## التطوير والاختبارات

```sh
npm test
npm run build
npm run dev
```

`npm start` يخدم النسخة المجمعة، بينما `npm run dev` يشغّل Vite بتحديث مباشر للواجهة داخل خادم Express على المنفذ نفسه. أوقف الخادم الحالي قبل تبديل نمط التشغيل. لا تشغّل عمليتين على مجلد بيانات PGlite نفسه.

الاختبارات تستخدم قاعدة PostgreSQL مدمجة في الذاكرة دون المساس ببيانات التطبيق. تغطي الدخول وCSRF، نطاق الموظفين والراتب، التعديلات المعلقة، سلسلة الموافقات والخصم المتزامن، التداخل والرصيد، إلغاء الطلب، المستمسكات والتشفير والتنبيهات، منع اعتماد الذات، التقارير، وتغيير الصلاحيات.

## التجهيز للنشر السحابي

المشروع جاهز للتشغيل كخادم Node.js أو حاوية Docker مع PostgreSQL مُدار. **لم يتم نشره على استضافة عامة ضمن هذا التسليم.**

1. جهّز PostgreSQL فارغًا واتصال TLS موثوقًا، ونطاق HTTPS أمام التطبيق.
2. استخدم `.env.production.example` كنموذج. لا تستخدم بيانات التجربة في قاعدة الإنتاج.
3. اضبط `NODE_ENV=production` و`SEED_DEMO=false` و`APP_ORIGIN=https://your-domain` و`DATABASE_URL`.
4. أنشئ `DOCUMENT_KEY` عشوائيًا بطول 32 بايت، ممثلًا في 64 حرف hex. مثال لإنشاء قيمة محليًا: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. احفظها في مدير أسرار، لا في المستودع.
5. شغّل `npm run db:migrate`. لإنشاء أول مدير على قاعدة فارغة، مرّر `ADMIN_USERNAME` و`ADMIN_NAME` و`ADMIN_PASSWORD` بطول 16 حرفًا على الأقل عبر متغيرات البيئة، ثم شغّل `node server/bootstrap-admin.js`. أزل متغير كلمة المرور بعد التنفيذ.
6. من حساب admin أنشئ حساب HR: يمكن منح admin مؤقتًا صلاحية إدارة السجل الوظيفي لإضافة الموظف الأول، ثم إنشاء حسابه بدور HR Manager وإزالة الصلاحية المؤقتة. جميع التغييرات تُسجل في Audit Log.
7. شغّل `npm run build` ثم `npm start`، أو ابنِ الحاوية باستخدام `docker build -t hr-leave-v1 .` وشغّلها مع متغيرات الإنتاج.
8. وجّه HTTPS إلى المنفذ 3000. استخدم `/api/health` للفحص. احصر شبكة PostgreSQL في خادم التطبيق، ولا تعرّض منفذها للعامة.

الخادم يرفض بدء الإنتاج دون PostgreSQL وHTTPS origin ومفتاح المستمسكات وتعطيل بيانات التجربة. ملفات الارتباط Secure في الإنتاج؛ لذلك يجب استعمال HTTPS فعليًا. لا تمنح دورًا تشغيليًا أوسع من المطلوب.

### المرفقات والنسخ الاحتياطي

- صور المستمسكات ومرفقات السجلات مشفرة بـ AES-256-GCM داخل أعمدة `bytea` في PostgreSQL، وتُقرأ فقط عبر API بعد فحص الجلسة والصلاحيات. لا توجد روابط عامة للملفات.
- في الوضع المحلي، ينشأ مفتاح في `data/document.key`. احتفظ بهذا الملف مع نسخ قاعدة البيانات، لكن في مخزن منفصل محمي.
- في الإنتاج، انسخ PostgreSQL دوريًا باستخدام خدمة النسخ المُدارة أو `pg_dump`، واحتفظ بـ `DOCUMENT_KEY` في مدير أسرار مع نسخة استرجاع آمنة. فقدان المفتاح يمنع فك تشفير المرفقات.
- اختبر الاستعادة في قاعدة منفصلة قبل الاعتماد على النسخ. توقف عن تشغيل PGlite قبل نسخ مجلد `data` محليًا لضمان نسخة متسقة.
- حماية Audit Log تمنع التعديل العادي، لكنها ليست إثباتًا تشفيريًا ضد مسؤول قاعدة بيانات يملك صلاحية تعطيل المشغّلات.

## هيكل المشروع

```text
src/
  main.jsx                 الشاشات والنماذج العربية
  api.js                   اتصال الخادم والتصدير والملفات
  styles.css               التصميم المتجاوب والطباعة
server/
  index.js                 تشغيل الخادم والجدولة
  app.js                   API والتحقق والموافقات والصلاحيات
  db.js                    موائم PostgreSQL / PGlite
  schema.sql               الجداول والقيود والفهارس
  security.js              الصلاحيات والتجزئة والتشفير
  seed.js                  الأدوار وبيانات التجربة
  migrate.js               تهيئة مخطط البيانات
  bootstrap-admin.js       مدير الإنتاج الأول
tests/integration.test.js  اختبارات دورة العمل والصلاحيات
Dockerfile / compose.yaml تجهيز التشغيل السحابي والمحلي
```

المخطط الأول قابل لإعادة التشغيل بأمان ومُسجل في `schema_migrations`. عند تطوير الإصدار التالي أضف ترحيلات مرقمة لترقية البيانات، ولا تعتمد على `CREATE TABLE IF NOT EXISTS` لتغيير أعمدة قائمة. الواجهة والخادم مستقلان في المصدر، ويمكن تقسيم وحدات `app.js` و`main.jsx` إلى حزم أصغر مع توسّع المنتج.

## حدود V1 الواضحة

لا يتضمن هذا الإصدار: الرواتب المحاسبية، الحضور، التوظيف، تقييم الأداء، تقويم العطل، الترحيل والاستحقاق الشهري، تفويض موافقات مؤقت، محرك سياسات قابل للتصميم من الواجهة، رسائل بريد/SMS، MFA/SSO، فحص برمجيات خبيثة للملفات، أو تقارير XLSX أصلية. التصدير الحالي CSV وPDF عبر الطباعة. لا تُرسل إشعارات خارج التطبيق.

توجد حدود للرفع والتحقق من توقيع نوع الملف والتشفير، لكن تشغيل النظام ببيانات موظفين حقيقية يتطلب مراجعة نشر وأمن وسياسة احتفاظ ونسخ احتياطي مناسبة لجهتك. تحديد محاولات الدخول افتراضيًا بذاكرة عملية الخادم؛ عند تشغيل عدة نسخ استعمل مخزنًا مشتركًا أو بوابة مركزية لتحديد المعدل. جدولة التنبيهات تعمل أثناء حياة الخادم، وتلحق التنبيهات الفائتة عند تشغيله مجددًا.
